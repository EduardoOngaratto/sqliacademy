Prevenção de SQL Injection

Consultas parametrizadas

A forma correta de evitar SQL Injection é não misturar código e dados. Em Java, com JDBC, isso é feito com PreparedStatement: a consulta é escrita com marcadores ? no lugar dos valores, e os valores são informados depois, por métodos como setString e setInt.

String sql = "SELECT titulo, ano FROM livro WHERE autor = ?";
PreparedStatement ps = conexao.prepareStatement(sql);
ps.setString(1, autor);
ResultSet rs = ps.executeQuery();

O texto do SQL chega ao banco sem nenhum dado do usuário, e o valor é enviado separado. Como o banco já conhece a estrutura do comando antes de receber o valor, este é tratado sempre como dado: buscar a autora D'Ávila funciona normalmente, e o apóstrofo é só mais um caractere do nome.

Os marcadores substituem apenas valores, e não partes da estrutura da consulta, como nomes de tabelas e colunas ou a direção de um ORDER BY. Quando essas partes precisam variar, a aplicação deve escolher entre opções fixas definidas no próprio código (uma lista de valores permitidos), nunca concatenando o que veio da requisição.

ORM

Frameworks ORM, como o JPA/Hibernate, mapeiam tabelas para classes Java e geram o SQL automaticamente. Os métodos de repositório do Spring Data (como findByAutor) e as consultas JPQL com parâmetros nomeados são parametrizados por padrão. Esta plataforma, por exemplo, acessa o banco só dessa forma.

@Query("SELECT l FROM Livro l WHERE l.autor = :autor")
List<Livro> buscarPorAutor(@Param("autor") String autor);

O ORM, porém, não protege de tudo. Uma consulta JPQL ou SQL nativa montada por concatenação volta a ter o mesmo problema, porque o texto da consulta passa a conter o dado do usuário:

// Vulnerável: a entrada vira parte do texto do JPQL
em.createQuery("SELECT l FROM Livro l WHERE l.autor = '" + autor + "'", Livro.class);

// Seguro: o valor vai como parâmetro nomeado
em.createQuery("SELECT l FROM Livro l WHERE l.autor = :autor", Livro.class)
        .setParameter("autor", autor);

A regra vale com ou sem ORM: o valor vindo do usuário entra sempre como parâmetro.

Boas práticas complementares

Validação no servidor. Conferir tipo, tamanho e formato das entradas (um ano deve ser um número dentro de uma faixa válida, um e-mail deve ter formato de e-mail) reduz erros e limita o que um atacante consegue enviar. A validação é um complemento das consultas parametrizadas, e não um substituto.

Menor privilégio no banco. O usuário de banco usado pela aplicação deve ter apenas as permissões de que precisa: por exemplo, sem permissão para apagar tabelas ou acessar outros bancos. Se alguma falha passar, o estrago fica limitado.

Mensagens de erro genéricas. Detalhes de erros do banco, como mensagens de sintaxe, nomes de tabelas ou o rastreamento da exceção, não devem ser exibidos ao usuário. Eles ajudam o atacante a entender como a consulta foi montada. O correto é registrar o detalhe no log do servidor e mostrar uma mensagem genérica.
